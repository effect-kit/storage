# AWS S3 adapter

The Node S3 adapter uses the official AWS SDK directly. It implements the portable
service and native copy, bulk deletion and multipart operations. Signing and POST
policies have separate entry points and optional peers.

Status: implemented with controlled HTTP and local RustFS evidence. Real AWS
acceptance is pending, at the owner's request. See [phase 3 evidence](evidence/phase-3.md).
The initial profile covers general-purpose buckets. It does not qualify directory
buckets, access points, Outposts, other S3 providers, Bun or Workers.

## Dependencies and entry points

| Import                           | Explicit peer                                 |
| -------------------------------- | --------------------------------------------- |
| `@effect-kit/storage/s3`         | `@aws-sdk/client-s3`                          |
| `@effect-kit/storage/s3/signing` | client-s3 and `@aws-sdk/s3-request-presigner` |
| `@effect-kit/storage/s3/post`    | client-s3 and `@aws-sdk/s3-presigned-post`    |

Development and local evidence use version 3.1159.0 of all three official packages.
They own native commands, credential resolution, XML error decoding and SigV4;
Effect Storage owns public contracts, source types, scopes, validation and outcomes.
No extra Effect AWS wrapper or managed-upload dependency is used. Core and /testing
continue to work without AWS peers. The S3 entry point does not load the signing peers.

## Portable usage and ownership

```ts
import { Effect } from "effect";

import { Storage } from "@effect-kit/storage";
import { S3Storage } from "@effect-kit/storage/s3";

const program = Effect.gen(function* () {
  const storage = yield* Storage;
  yield* storage.put({
    key: "notes/example.txt",
    body: new TextEncoder().encode("hello"),
    contentType: "text/plain",
    condition: { _tag: "CreateOnly" },
  });
  return yield* Storage.getText({ key: "notes/example.txt", maxBytes: 1024 });
});

// bucket and region are application configuration; omitting credentials selects
// the native SDK's default credential chain.
const live = S3Storage.layer({ bucket, region });
```

`layer` provides Storage, S3Storage and StorageCopy from one owned client.
`make(config)` returns S3StorageService inside Scope. Its client is destroyed at
scope release. Reuse a Layer value to share its acquisition in an Effect graph.

`layerConfig()` reads S3_BUCKET and S3_REGION through Effect Config. A supplied
`Config<S3Config>` can assemble additional settings. Configuration failures are
sanitized; no process-wide environment variables are changed by the adapter.

`makeClient(client, config)` / `layerClient(client, config)` borrow a client and
never destroy it. A borrowed configuration must supply a stable storeId, matching
region/endpoint/addressing, and no credentials override. Configure its credentials
on the client. Its policy must use maxAttempts=1, no region redirects, and
WHEN_SUPPORTED request/response checksum protection. Mismatches fail construction.
The native client escape hatch retains these ownership rules; do not serialize it.

Configuration accepts native static credentials or a refreshable provider. The
default chain is useful for locally configured profiles and workload identity;
no additional credential-provider package is required for that path. Providers
remain refreshable. Returned config omits the supplied credentials object.

Endpoints are privileged configuration: only trusted application code should set
them. Only HTTP(S) origins without credentials, paths, query or fragments are
accepted. A custom endpoint is not a verified named provider profile. SSE-C requires
HTTPS. Generated store IDs bind endpoint/region/bucket; explicit identities remain
the caller's namespace responsibility.

## Streams, identity and request policy

Known-length Effect streams use a Node backpressure bridge. Caller E/R, defects
and interruption retain their identity; a failed producer aborts its request.
Supply contentLength for streaming large objects. Declared/actual length mismatches
and byte limits fail explicitly.

Unknown-length streams are staged before sending, up to maxUnknownLengthBytes
(default 16 MiB), further narrowed by request.maxBytes. They are not unbounded
single-request streams. Staging copies chunks and concatenates them, temporarily
retaining approximately twice the payload plus runtime/source overhead. This is
a per-operation logical limit, not an aggregate memory guarantee. Phase 4 owns
managed strategies and concurrent byte budgets.

Native single PUT/part limits and multipart constraints are exported as s3Limits.
Oversized unknown uploads need a known-length source or explicit multipart use.
There is no automatic multipart promotion or source replay in this adapter.

S3 keys preserve opaque spelling and enforce 1024 UTF-8 bytes. Metadata rejects
case-colliding names and a user-metadata payload over 2048 bytes. Header values must
also be representable by the Node HTTP transport. Native service limits remain
authoritative. Portable key/header acceptance alone does not prove S3 acceptance.

GET metadata and body come from one response. Ranges report returned bounds and
complete object size separately and reject an unexpected Content-Range. SDK bodies
are closed for unread, partial and interrupted consumption. A 304 has no body;
its metadata contains the requested reference without fabricating missing fields.
PUT/copy/complete receipts never perform a racing HEAD to fill absent fields.

ETags remain opaque. S3Version IDs remain strings, including the native null-version
identifier. Other providers' version kinds are rejected. Versioned delete semantics
are native: deleting a key can create a marker; deleting a ref targets that version.
Archive availability, restore and version enumeration are later lifecycle work.

Native listing uses query/store-bound, versioned cursor envelopes. They carry a
provider continuation token and survive reconstructing the same store identity
subject to provider token validity. They are not authenticated grants or snapshots.
Empty pages with continuation remain traversable.

Owned clients use one SDK attempt with no automatic outer retry. requestTimeoutMillis
(default 30 seconds) bounds each SDK request/signing acquisition, not a whole transfer
or caller-controlled body-consumption lifetime. Interruption forwards AbortSignal.
Request failure after possible transmission can be unknown; cancellation cannot undo
a committed mutation. Phase 4 coordinates transfer deadlines/retries/reconciliation.

SDK checksum protection remains enabled for data operations. Native putObject options
support explicit checksum algorithms/values, storage class and tags. Metadata records
algorithm, encoding, full/composite meaning and observed part count separately from
ETag. Tests qualify specific CRC32/SHA256 paths, not every algorithm/provider pairing.

## Native operations and encryption

S3Storage supplies putObject(request, options), copyObject, copyPart, deleteObjects,
and multipart. The narrow Storage service remains unchanged.

copyObject supports sourceIfMatch, pinned sources, destination conditions,
metadata/tag directives and configured encryption. Pass a source S3StorageService
as its second argument for an explicit cross-bucket namespace. The destination
client's credentials need source read authority; a source client's credentials are
not forwarded. Separate custom endpoints cannot perform native copy. Native copy
size/region/account constraints remain provider-enforced; use copyPart for multipart
strategies. Embedded HTTP 200 errors are decoded by the official SDK.

deleteObjects accepts 1–1000 distinct unconditional targets and returns ordered
per-target Result values. Missing or lost receipts remain unknown. Conditional batch
deletes are explicitly unsupported; Storage.deleteMany uses per-object operations
when conditions are needed. Native per-key failures never disappear into HTTP success.

multipart supplies initiate, uploadPart, listParts, listUploads, complete and abort.
Handles retain redacted upload IDs and selected checksum policy. Initiation selects
CRC32/COMPOSITE by default; CRC64NVME defaults to FULL_OBJECT. Native inventory
retains observed algorithm/type fields for recovery. Completion sorts
parts and rejects duplicates and known undersized nonfinal parts. Part checksums
describe each part's payload. Part/upload inventory cursors bind their session/query.
Upload listings with delimiter are explicitly unsupported by this result contract.
Complete/abort can have unknown outcomes; the library does not silently repeat them.
Persisting checkpoints, orphan workers and restart recovery are phases 4–5.

Configured encryption supports AES256, KMS/DSSE-KMS settings and redacted SSE-C keys.
The SDK owns native encoding. SSE-C settings accompany part/read/copy operations;
KMS settings apply at object/upload creation. KMS permissions and hosted encryption
behavior remain unqualified here. Object Lock/governance is phase 10.

## Signing, POST forms and public URLs

S3Signing.make(storage) supplies sign and signPart. S3Signing.layer requires
S3Storage and provides both S3Signing and portable StorageSigning; compose it with
`Layer.provideMerge` when the application also needs the storage service.

sign supports GET/HEAD/PUT/DELETE. PUT accepts headers, conditions, contentLength
and precomputed checksums. SignPart binds upload/part identity. Grants contain method,
redacted URL/required headers, effective expiry and provider-enforced header constraints.
Send the returned headers unchanged. Credential lifetime caps requested expiry, and
each new grant resolves credentials again. Revocation/policy changes can invalidate
a grant earlier. These are reusable bearer grants, not single-use uploads.

The signing-only client does not compute an empty-body checksum for an unknown
future PUT payload. Supply a precomputed checksum to bind its bytes. This does not
disable data-plane checksum protection. Raw keys, tokens, bearer URLs and SDK messages
are excluded from public StorageErrors.

S3Post.make(storage).create accepts an exact key, expiry, min/max bytes, contentType
and metadata. Returned fields and URL are redacted; the SDK builds enforced policy
conditions. Filename interpolation is rejected. POST with configured encryption,
expected owner or requester-pays is explicitly unsupported rather than dropping that
authority. Browser CORS and backend verification are phase 11 work.

S3Storage.publicUrls(baseUrl) is an optional StoragePublicUrls Layer. The explicit
base must end with a slash; it does not change bucket/object visibility. Versioned
refs and dot-segment keys are rejected for this resolver to avoid identity loss
through URL normalization. Private delivery should use signed requests.

## Verification and permissions

`pnpm test:s3:local` creates a pinned RustFS container with disposable credentials,
a versioned bucket and owned test prefixes. It runs public conformance and native
acceptance, then removes its container and credential file. Docker is required.
`.github/workflows/s3-local.yml` is an optional manually dispatched lane.

For later AWS acceptance, supply STORAGE_S3_ACCEPTANCE=aws, STORAGE_S3_TEST_BUCKET,
STORAGE_S3_TEST_REGION and STORAGE_S3_TEST_PREFIX, then run `pnpm test:s3:aws` with
an externally configured profile/role. The bucket must already have versioning enabled.
Endpoint overrides are rejected for AWS mode. The suite creates unique subprefixes
and cleans only their uploads, versions and markers; it does not change bucket policy,
IAM, CORS, versioning or retention, or delete the bucket.

Grant object read/write/delete and multipart permissions only under the authorized
prefix. Versioned tests need GetObjectVersion/DeleteObjectVersion; inventory/cleanup
needs bucket ListBucket/ListBucketVersions/ListBucketMultipartUploads and
ListMultipartUploadParts/AbortMultipartUpload, constrained by prefix where supported.
Signing uses the same principal's corresponding object permissions. Encryption needs
the separate KMS permissions appropriate to the chosen settings. Application roles
should receive only their required operations; test cleanup is a broader dedicated role.

Local success cannot certify AWS IAM, region routing, account/KMS behavior, hosted
consistency or all failure windows. AWS acceptance remains pending; no compatible
provider is qualified by this fixture.
